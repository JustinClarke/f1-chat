## 1. MVP chat app (2026-10-14, files created about 10:28 local)

What was built (verified by reading the code):
- `web/src/db.ts`: starts DuckDB-WASM in the browser, fetches `/manifest.json` from the data server, registers each 2024 Parquet file over HTTP, and creates two views, `laps` and `results`. The views add `race` (parsed from the `race=` folder in the path) and `session` (`'Q'` if the path contains `/session=Q/`, otherwise `'R'`), and drop a few mostly-null columns.
- `server/serve-data.mjs`: a read-only static server on port 8000 with CORS and HTTP Range support, because DuckDB-WASM cannot glob a folder over HTTP. It serves only `.parquet` files and refuses the `telemetry` folder.
- `worker/index.ts` and `wrangler.toml`: a Cloudflare Worker with a `POST /chat` route. It passes `messages` and `tools` to the Workers AI binding and returns the JSON.
- `web/src/chat.ts`: the loop. It builds a system prompt (data guide, schema summary, rules), calls the model with one tool, `run_sql`, validates the SQL, runs it in the browser, returns up to 50 rows to the model, and lets the model answer. Limits: 8 model steps per question, and 2 SQL errors before it gives up.
- SQL validation (`validateSql` in `web/src/chat.ts`): one statement only, must start with SELECT or WITH, a keyword block list (insert, update, delete, drop, attach, copy, pragma, install, load), and `LIMIT 200` appended if no `limit N` appears anywhere in the text.
- `web/index.html`, `web/src/main.ts`: a plain page with a log, an input box, a "Use exploration notes" checkbox and an "Explore schema" button.

Why this design: the user wanted a browser chat where the model does not touch data directly. It writes SQL and the browser executes it, so the data stays local and the Worker only proxies model calls.

Result: it ran and answered questions. The first model's behaviour was poor on aggregate questions.

What went wrong, a real failure. The first model answered the question "who won the most races in 2024" with "Oscar Piastri won the most races, 1432 wins" (from the brief). The reason is visible in the logged SQL: it counted rows in the `laps` table (one row per driver per lap) instead of counting race wins in `results`. A race win is a row in `results` with `session = 'R'` and `Position = 1`. The earliest results file, `eval/results-2026-10-14T06-54-10-175Z.json`, shows the same family of error (verified): with notes off it answered "Pierre Gasly ... 1432 wins", and with notes on "PIA ... 1432 wins", both from SQL of the form `SELECT Driver, COUNT(*) ... FROM laps WHERE session='R'`. That file does not record which model produced it, so linking it to the first model is inferred. Two other answers in that file were wrong too: Norris's Monaco laps (77 instead of 78) and the unanswerable question (it said "Charles Leclerc won the 2024 Monaco Grand Prix" for a question about 2023, so it answered from outside knowledge and the wrong year).

Lesson: the model has no idea what one row means unless told. That led directly to the data guide (section 6).

## 3. Schema exploration round and the `llm_notes` table (2026-10-14)

What was built (verified): `web/src/profile.ts` computes a deterministic profile of each view in SQL (null counts, distinct counts, min and max, value lists for low-cardinality columns, a seeded 5-row sample, and candidate unique keys). `web/src/explore.ts` gives the model that profile plus two tools, `run_sql` and `save_note`, with a budget of 8 tool calls and 12 turns. `save_note` stores a note in an in-memory DuckDB table `llm_notes` (topic, claim, evidence_sql, evidence_result, confidence). With "Use exploration notes" ticked, the notes are appended to the system prompt in `web/src/chat.ts`.

Why: the idea was that the model could learn the data's traps (grain, units, how to find winners) once, and reuse that knowledge, instead of someone writing a guide by hand.

Result: no improvement (verified from the two results files):
- Run 1 (06:54Z): 6 notes saved. Three are identical column lists for `laps` and one is a column list for `results`, for example "The laps table includes columns for time, driver, driver number, lap time, lap number, stint ...". The others say "each row is a lap" and "each row is the final result of a driver in a race". Nothing about units, nothing about wins.
- Run 2 (07:04Z): 1 note saved, "laps table grain and key". The model spent its 8 tool calls on key-uniqueness checks, repeating one query.
- Notes off vs notes on, in the same files: 7 vs 8 pass (run 1), 10 vs 10 (run 2). That is inside noise for one repeat per question.
- Run 1's notes-on answer for the wins question still said "PIA ... 1432 wins", so the notes did not fix the main failure.

What went wrong: the notes were weak and restated column names. The save check was also weak (verified in `web/src/explore.ts`): it re-runs `evidence_sql` and only rejects the note if that SQL errors. It never checks that the SQL result supports the claim. A note that says anything, with any valid query attached, is saved with confidence "high". The `high` labels were therefore meaningless.

Status: the code is still in the app and still reachable from the UI. It was dropped from the experiment (`run_experiment.mjs` runs with notes off). The README still describes it as a main feature.

## 5. Strict scorer `eval/score.mjs` and the U+202F bug (2026-10-14)

What was built: a scorer that compares an answer to `expected_values` in `questions.json`. Rules (verified by reading `eval/score.mjs`): normalise text (NFKC, all Unicode spaces to a normal space, dashes to a hyphen); parse times such as `1:21.432` into seconds and numbers such as `13,514` or `13 514`; numbers must match exactly; times must be within 0.5 ms and a value of 1e6 or more is also tried as nanoseconds; names must appear as whole words, ignoring case and accents; the unanswerable question needs a refusal phrase and no driver name. Answers that begin "Gave up" or "Stopped" fail. Only the refusal case can return "check manually".

The bug (verified from the two results files): gpt-oss-20b writes a narrow no-break space (U+202F) in output, for example `Red<U+202F>Bull<U+202F>Racing` and `Max<U+202F>Verstappen`. The first scorer matched names with a literal space, so a correct answer, "Red Bull Racing won the most races in 2024, with 9 victories", was marked "check manually" in both runs of `wins_team` in the 07:04Z file. The fix is the normalisation step. `eval/score.test.mjs` has a regression test for it. I ran `node --test eval/score.test.mjs` today: 5 tests, all pass.

Other scorer facts worth knowing:
- It is lenient in one way: for number and time checks, a match is any number anywhere in the answer. An answer that contains the right number in an unrelated place would pass. Not seen in practice, but possible.
- It is lenient in another way, and this one matters for `bahrain_clean_pace`: the "faster driver" check is a name check. Since the question names both Verstappen and Norris, any answer that mentions Verstappen passes this check, even if the answer says Norris is faster. The two medians are checked as numbers but not tied to a driver. An answer that swapped the two medians between drivers would pass. I read the first ~170 characters of the 13 passing answers for that question and saw no swap, but I did not audit all 20 runs per variant or the later parts of long answers.
- Answers given in nanoseconds pass a time check because of the 1e6 rule.

## 6. Data guide `web/src/dataGuide.ts` (2026-10-14)

What was built: a hand-written text block, about 76 lines, that is placed in the system prompt on every question. It explains the grain of each table, the nanosecond units, derived columns, one line per column, and a "how to answer common questions" section: wins are `results` rows with `session = 'R' AND Position = 1`, laps are counted as rows, and so on. That last section is aimed straight at the 1432-wins failure.

Why: exploration (section 3) had not produced useful knowledge, so the knowledge was written by hand.

Result: in the later runs the model answered the aggregate questions correctly (section 9: V3, the full guide, passed 17 of 20 on four hard-ish questions; the old 07:04Z run passed 10 of 11). Whether the guide caused this is not isolated by a controlled test except in the 2026-10-15 experiment, whose result was mixed.

What went wrong: the file header says "Verified against the raw FastF1 Parquet (2024 Bahrain files)". Several descriptions were written from memory of how the FastF1 library behaves, not from looking at the data. Today I checked a few against all 24 races with the Python DuckDB package (read-only; these are my checks, not the original author's).

Found wrong or misleading in the data (verified today):
- `results.Laps`: the guide says "Present only in qualifying files". In the 2024 files it is NULL in every row, qualifying included (0 non-null of 958 rows). Wrong.
- `results.Status`: the guide's examples include `'+1 Lap'` and `'Collision'`. The actual values in race rows are only `Finished` (287), `Lapped` (138), `Retired` (49), `Did not start` (3), `Disqualified` (2). Those two examples do not exist.
- `results.ClassifiedPosition`: the guide lists letters R, D, E, W, F, N. The race rows contain only numbers plus `R` (43), `W` (3) and `D` (1). `E`, `F` and `N` never occur. In qualifying the column is an empty string (479 rows), not a number or a letter.
- `results.Time`: the guide says NULL for "drivers who ... were lapped out of time". Lapped finishers do have a Time (137 of 138 rows non-null, smallest gap 0.873 s). Only Retired, Did not start and Disqualified rows are NULL. The guide's statement is at least misleading.
- `laps.Compound`: the guide lists `UNKNOWN`. The data also contains the literal string `'None'` (3 rows), which the guide does not mention.
- `laps.Position` is NULL in 28 race rows; the guide implies a value for every lap.
- Checked and fine: 24 distinct race_id values, and exactly 24 race rows with Position = 1 (one winner per race). I did not separately check the pole-position rule or the points rule.

Not checked by anyone I can find (written from FastF1 knowledge or plausible guesses, treat as unverified):
- `TrackStatus` code meanings ('1' green, '2' yellow, '4' safety car, '5' red, '6' VSC, '7' VSC ending). The distinct codes in the data are combinations of 1, 2, 4, 5, 6, 7, which is consistent, but the meanings were not checked against an official source.
- `LapTime` "NULL for the first lap of a stint and for laps with no valid timing". Only the count was seen (225 NULL race laps of 26,606, none on all stint starts). The stint-start claim is unchecked and probably wrong, since 225 is far fewer than the number of stints.
- `Stint` ("incremented after each pit stop"), `TyreLife`, `FreshTyre`, `IsPersonalBest` ("fastest lap in the session so far"), `IsAccurate`, `FastF1Generated`, `LapStartDate`, `DeletedReason`.
- Speed trap meanings: `SpeedI1`, `SpeedI2`, `SpeedFL`, `SpeedST`.
- Qualifying rules: "Q2 for the top 15, Q3 for the top 10". Non-null counts (Q1 474, Q3 235 over 24 weekends) are roughly consistent but not exact.
- Points: "25 for a win down to 1 for 10th" is outside knowledge. The guide also tells the model not to use outside knowledge.
- `race_id` ("do not use for filtering") and `index`, `TeamColor`, `DriverId` as "ignore" columns: never tested.
- The `Time` column semantics for the winner (total time) vs others (gap): consistent with the data I saw (winner 4,480 s to 8,595 s; others 0.6 s onward), so mostly verified.

Action: fix or soften the wrong lines above before relying on the guide for new questions. Any change to `dataGuide.ts` changes the V3 prompt, so regenerate `eval/variants/v3.txt` with `node eval/variants/make_v3.mjs` (the experiment runner refuses to start if they differ).

## 8. Ollama and Qwen3-4B local test (2026-10-14, log `eval/logs/2026-10-14T07-36-53-181Z/`)

What was built: `run_eval.mjs` has an escape hatch. If `LLM_URL` is set (for example `http://localhost:11434/v1`) the runner sends the app's request to Ollama's OpenAI-compatible `/chat/completions` instead of the Worker, adds `model: $LLM_MODEL`, and sets `reasoning_effort: "none"` unless `LLM_THINK` is set. The app code is unchanged. The model used was `qwen3-4b-16k`, a custom Ollama model whose definition is not in the repo (see below).

Why: the cloud quota was gone, and a local model has no quota. It also tests whether a 4B model can do the task at all.

Problems, in order (what I could verify is marked):
1. Context truncation. Ollama's default context window was 4096 tokens. The system prompt with the data guide is 11,613 characters, about 3,765 prompt tokens (verified from `usage`), and the model also generates a long reasoning trace. Prompt plus output overflows 4096, so the prompt gets truncated and the model loses the beginning (the instructions). The fix was a 16K variant, `qwen3-4b-16k`, presumably made with a Modelfile setting `num_ctx 16384`. The Modelfile is not stored in the repo, so recreating it is on the next person. The truncation story is from the brief; the log shows the final model name and the prompt sizes only.
2. Thinking-token latency. Qwen3 "thinks" before answering. Even with `reasoning_effort: "none"` the logged completions are 1,200 to 2,800 tokens, and the first call of each run took 95 to 233 seconds (verified). A full question took 30 to 302 seconds. The setting `reasoning_effort: "none"` did not stop the thinking (inferred from the token counts and from the text, see item 4).
3. The 300-second timeout. One run, `team_wins_and_points|guide=off`, failed after 302 seconds with `TypeError: fetch failed` (verified). The runner passes `AbortSignal.timeout(900_000)` for Ollama, so the 15-minute limit was not what fired. The 300 s matches the default headers timeout of Node's built-in `fetch` (undici), which waits for response headers and Ollama sends none until the answer is ready. That diagnosis is inferred; the error text does not name the cause. The code has no fix (no custom dispatcher with a longer `headersTimeout`), so any call slower than 5 minutes will fail the same way.
4. Thinking text leaks into the answer. Every logged `final_answer` starts "Okay, let's see. The user asked ..." and contains a `</think>` tag before the real answer (verified). The scorer reads the whole text, thinking included. A pass could therefore come from a number that only appears in the reasoning. For the Ollama runs, "pass" means "the right values appear somewhere in the text", which is weaker than for gpt-oss-20b. Strip everything up to `</think>` before scoring, or fix the Ollama setting.

Results so far (7 runs; 1 repeat; the run was cut short, there is no `summary.md` and the 8th run, `unanswerable|guide=off`, is missing):
- Guide on: 4 of 4 pass (`wins_team` 180 s, `team_wins_and_points` 205 s, `top_compound` 163 s, `unanswerable` 30 s).
- Guide off: `wins_team` fail ("Red Bull Racing won 19 races", the same wrong answer gpt-oss-20b gave in V0 and V1 of the experiment, section 9), `top_compound` fail (13,770 instead of 13,767), `team_wins_and_points` error (the timeout above).
- One repeat per cell is not evidence. The only fair reading is "it can work with the guide, slowly, and the guide-off failures look like the cloud model's".

Open: whether to continue with a local model at all. At 2 to 5 minutes per question it is too slow for a chat UI on this machine, at least with thinking on.

## 9. Prompt-variant experiment (2026-10-15)

The full archive is `experiments/2026-10-15-prompt-variants/` (README, PROTOCOL, DECISIONS, ISSUES, HOW_TO_RERUN, `results/`). This section summarises it and adds my checks. The experiment's own README says "App commit: none".

Question: does the amount of data description in the system prompt change correctness or latency for gpt-oss-20b?

Design (verified from `PROTOCOL.md` and `eval/run_experiment.mjs`): four variants that differ only in the data-guide text.
- V0: none (`v0.txt` is empty).
- V1: shorthand, 1,125 bytes.
- V2: medium, 3,227 bytes, includes recipes for common questions.
- V3: the full `dataGuide.ts`, 6,530 bytes.
Four questions: `wins_team`, `top_compound`, `bahrain_clean_pace` (added to `ground_truth.py` for this experiment), `unanswerable`. Five repeats each, 80 runs, order shuffled in blocks with a seeded generator (seed 20261015). Frozen settings sent with each request: temperature 0, reasoning effort "medium", max_tokens 4096, row limit 50. The same rule text, about the rows returned by `run_sql`, was added to every variant. Fresh app module and new DuckDB instance per run. Hypotheses H1 to H4 and thresholds for "suggestive" were written before the first run.

Pilot: one run of V3 on `bahrain_clean_pace`, logged to `pilot.jsonl`, not counted.

Totals (verified by recounting `results/runs.jsonl` today): passes out of 20 were V0 12, V1 15, V2 15, V3 17. Overall 59 pass, 20 fail, 1 "check manually", 0 infrastructure errors.

By question (passes of 5):

| question | V0 | V1 | V2 | V3 |
|---|---|---|---|---|
| wins_team | 3 | 1 | 5 | 5 |
| top_compound | 4 | 5 | 0 | 4 |
| bahrain_clean_pace | 1 | 4 | 5 | 3 |
| unanswerable | 4 (+1 CHK) | 5 | 5 | 5 |

Median latency (s): V0 3.93, V1 2.63, V2 2.55, V3 3.34. Median prompt tokens: 3,652, 4,242, 5,317, 7,023. Median neurons per run: 78, 82, 102, 133.

Why no hypothesis is clearly supported (my reading against the protocol's own thresholds; this is my reading, not a statistical test):
- H1 (V2 matches V3 accuracy at lower latency and fewer tokens): accuracy 15 vs 17 is inside the "no detectable difference" band (under 6). Tokens are lower for V2. Latency is lower overall (2.55 vs 3.34), but the sign is the same in only 2 of 4 questions (lower on `top_compound` and `bahrain_clean_pace`, higher on `wins_team` and `unanswerable`), and the protocol asked for at least 3 of 4. Not supported.
- H2 (V0 clearly worse than V1): 12 vs 15, a gap of 3, under the 6 threshold. Not supported overall, though the per-question gaps differ in direction (`wins_team` V0 3 vs V1 1; `bahrain_clean_pace` V0 1 vs V1 4).
- H3 (V1 between V0 and V2): V1 and V2 tie at 15. Cannot tell.
- H4 (latency rises V0 to V3): the medians are 3.93, 2.63, 2.55, 3.34, which is not monotone. Not supported. V0 is slowest, mostly because it needs more tries on `bahrain_clean_pace` (median 9.67 s).
- The null (no difference between any pair) is not rejected on overall totals. Individual cells show gaps of 3 or more (the protocol's "suggestive" level), but each of these has a specific explanation below, so they do not support a clean story about guide length.

Mistakes and causes of failures:
1. Wording mistake in V2 (my file, per ISSUES.md). V2 includes the recipe "Fastest race lap ... LapTime IS NOT NULL and Deleted is not TRUE" (line 39 of `v2.txt`, verified). On `top_compound` the model copied "Deleted is not TRUE" into a plain lap count and answered HARD with 13,612 laps instead of 13,767, five times out of five. So V2's 0 of 5 on that question is caused by how I wrote the recipe, not by V2 being a "medium" description. It drags V2's total down by up to 5 and breaks any comparison of V2 against the others. A rerun with the wording fixed was not done.
2. `wins_team` failures in V0 (2 of 5) and V1 (4 of 5): the answer was "19 victories" for Red Bull, because the SQL left out `session = 'R'` and so counted qualifying pole rows as wins. V1's shorthand says "results: one row per driver per session" but has no recipe; V2 and V3 have the explicit recipe and got 5 of 5.
3. Rounding in clean-pace answers. V3 failed 2 of 5 on `bahrain_clean_pace` only because the answer rounded the medians to two decimals ("95.48 s, 96.54 s"). The scorer needs 0.5 ms precision, so it rejects them. The values are close to correct. The Norris median is 96.5365 s, which ends in half a millisecond, so even a three-decimal answer (96.536 or 96.537) sits at the edge. The scorer, not the model, makes this look like a failure. The same rounding in other variants passed only when the answer also printed the full nanosecond value (for example V2 rep 1, "96.54 s (96 536 500 000 ns)"). So the V3 vs V2 result on this question depends on whether the model happened to print nanoseconds. The runner records an informational 1 ms check (`within_1ms_info`) that never changed a verdict.
4. V1 once answered the clean-pace question with nonsense values (1,000,000,000 and 1,050,000,000 ns).
5. V0 failed `bahrain_clean_pace` 4 of 5 with medians off by 0.1 to 1 s or wrong filters (they were not told what green-flag means in `TrackStatus`).
6. The "faster driver" check passes whenever the answer names Verstappen, which always happens (section 5). So a swapped answer could pass. Not audited across all 20.
7. The model's SQL was never compared to the ground-truth SQL; only the final answer is scored.
8. Crash after 40 runs: "JavaScript heap out of memory" (in `results/grid.log`). Each run makes a new DuckDB-WASM instance and they are never freed. The runner gained `MAX_RUNS` and the grid was resumed in batches of 14. The runner was edited after the protocol was written (neuron logging and `MAX_RUNS`); the SHA-256 of `eval/run_experiment.mjs` today (`9f789b40...`) is not the one in PROTOCOL.md (`30c09395...`) for that reason (verified by hashing). Prompts, settings and scoring were not changed.
9. Neither temperature 0 nor reasoning effort can be shown to work (section 10). A repeat-determinism test was never run, so run-to-run noise at "temperature 0" is unknown.

What the experiment does support, cautiously: a recipe that spells out "wins = results rows with session R and Position 1" removes the 19-wins error (V2 and V3 scored 5 of 5, V0 scored 3 of 5, V1 scored 1 of 5). The shorthand-only description (V1) did not. The raw totals (12, 15, 15, 17) point the same way as "more description helps a bit" but sit inside the experiment's own noise band.

Cost note: the grid is about 8,000 neurons, nearly the whole daily free quota.

Structure note: `experiments/2026-10-15-prompt-variants/` is a copy. The live files are `eval/experiment/` (logs and summary) and `eval/variants/`. I diffed them today: results files and variant texts are identical; the only differences are `PROTOCOL.md` (not in `results/`) and `HASHES.txt` (not in `eval/variants/`). `eval/experiment/PROTOCOL.md` is identical to the archived one.

## 10. Worker edit: forward temperature, max_tokens and reasoning (2026-10-15)

What was done (verified in `worker/index.ts`): the Worker used to send only `messages`, `tools` and `max_tokens: 2048`. It now also accepts `temperature`, `max_tokens` and `reasoning` in the request body and forwards each one only when present; `max_tokens` defaults to 2048. The browser app still sends none of the three. Only `eval/run_experiment.mjs` sends them (temperature 0, reasoning `{effort: "medium"}`, max_tokens 4096).

Why: the experiment needed a fixed temperature and a larger token budget so reasoning plus a tool call could not be cut off.

What was never verified (ISSUES.md and DECISIONS.md, and I found nothing to contradict them):
- The request returned HTTP 200, but nothing proves the model service honours `temperature: 0`.
- Two probe calls with reasoning effort low and high returned identical token counts, so the setting had no observable effect through this route. The parameter name `reasoning_effort` (instead of `reasoning: {effort}`) was not tried. The response contains no reasoning-token breakdown, so "reasoning tokens" are n/a in the summary.
- Whether `max_tokens` 4096 vs 2048 changed any outcome was not tested.

Consequences: the experiment's numbers are for a configuration (4096 tokens, temperature 0 requested) that the shipped app does not use. The app runs with 2048 tokens and no temperature. Results may not transfer.

## 11. Smaller observations from reading the code (2026-10-15)

- `web/src/main.ts` never calls `resetChat()`. `history` in `chat.ts` is a module-level array that is appended to on every question, including all tool results (up to 50 rows each). Context grows without limit during a session, and prior wrong answers stay in view. Only the harnesses reset it.
- `chat.ts`: if a question hits the SQL error limit or the 8-step limit, it returns early. When an assistant turn has several tool calls and the limit hits partway, tool results for the remaining calls are never appended. The next question would then send an assistant message with unanswered `tool_calls`, which many chat APIs reject. This is inferred from the code; I did not reproduce it.
- `validateSql`: the keyword block list is word-based, so a column or string containing one of those words (for example the literal 'load' in text) is rejected. A `;` inside a string literal is rejected. `LIMIT 200` is skipped if any `limit N` appears anywhere, even in a subquery, so the outer query may be unlimited. Functions such as `read_csv` or `read_parquet` are not blocked; inside the browser sandbox this reads only URLs and files the page can reach, so the risk is small but real.
- `ask()` does not catch a failing Worker call mid-question: the exception goes to `main.ts`, which prints it, but the history keeps the dangling user message.
- The Worker allows any origin (`Access-Control-Allow-Origin: *`). Fine for local dev, not for deploy. The README says so.
- `server/serve-data.mjs`, `eval/run_eval.mjs`, `eval/run_experiment.mjs` and `eval/ground_truth.py` all hard-code `/Users/justin/github/off-the-pace/data` as the default data root (override with `DATA_ROOT`). `ground_truth.py` also reads the raw `bronze` Parquet, the same source as the app, so the ground truth and the app share a data source (they differ in code, not in data).
- `esbuild`, used by the eval and experiment runners and by `make_v3.mjs`, is not in `package.json`. It comes in transitively through Vite, so a Vite upgrade could silently drop it.
- `package.json` has no script for the experiment runner, the scorer tests, or the Python ground truth.
- `.wrangler/` exists at the repo root (ignored); no `.dev.vars` or `.env*` file exists in this repo (verified with `ls -a`). The AI binding uses the Cloudflare login, not a key in the repo.
- `npx tsc --noEmit` (`npm run typecheck`) passes today with no output (verified).
