# Handoff: F1 chat (off-the-pace-chat)

Written 2026-10-15. Start here if you have no memory of earlier work. Full history, with mistakes: [BUILD_LOG.md](BUILD_LOG.md). The most recent experiment: [experiments/2026-10-15-prompt-variants/README.md](../experiments/2026-10-15-prompt-variants/README.md).

Tags used below: "verified" means I read the code or ran something today. "Inferred" means I deduced it. "From the brief" means the user told me and I found no proof in the repo.

## 1. What the project is

A browser chat where a user asks questions about 2024 Formula 1 data in plain English. A language model (on Cloudflare Workers AI) writes DuckDB SQL through one tool, `run_sql`. The browser runs that SQL on DuckDB-WASM against Parquet files served from a local data server. The model then writes the answer from the rows it gets back. The data is two tables, `laps` (one row per driver per lap) and `results` (one row per driver per session), for the 24 Grand Prix weekends of 2024, race and qualifying only.

## 2. Current state in one paragraph

The app works end to end (verified by reading the code and by the eval logs; I did not start it today). On the 12-question set, gpt-oss-20b with the full data guide mostly answers correctly, but only a small, partial evidence base exists: one repeat on most questions, and a 4-question, 80-run experiment where the full guide passed 17 of 20 and no guide passed 12 of 20, a gap too small to call. Not working or not trusted: the "exploration notes" feature (no measured benefit), the data guide (some lines are wrong, see Known issues), the local Ollama path (too slow, thinking text leaks into answers), and the scorer (it can pass a swapped answer). Blocking: nothing is committed (no git history at all), the app and the experiment use different model settings, and the Workers AI free quota (10,000 neurons a day) limits how many cloud runs you can do in a day.

## 3. How to run it

Prerequisites: Node 20 or newer (this machine has v26.5.0), `npm i` already done, the Parquet data at `/Users/justin/github/off-the-pace/data` (it contains `bronze/laps` and `bronze/results`), and a Cloudflare login. Check the login with `npx wrangler whoami`; if you are not logged in, run `npx wrangler login` yourself (it opens a browser). Do not run `wrangler deploy`; the Worker allows any origin.

Quota: the Workers AI free tier is 10,000 neurons per day. The 80-run experiment used about 8,000. The whole 11-question eval with exploration used up a day's quota once (BUILD_LOG section 7). When it runs out, calls fail with "AiError: 4006". The runners label that as an infrastructure error, not a model failure.

All commands run from `/Users/justin/github/off-the-pace-chat`, one terminal each.

1. Data server (port 8000): `npm run data`. To use another data folder: `DATA_ROOT=/path/to/data npm run data`.
2. Worker (port 8787): `npm run worker`. This is `wrangler dev`; the AI binding runs remotely, so it needs the login and it spends quota. Wait for "Ready on http://localhost:8787".
3. Web app (port 5173): `npm run dev`, then open http://localhost:5173. The page says "Ready." when DuckDB has loaded the files.
4. Typecheck: `npm run typecheck` (passes today, verified). Scorer tests: `node --test eval/score.test.mjs` (5 pass today, verified; not in any npm script).
5. Eval runner (needs steps 1 and 2 running): `npm run eval`. Useful options, all environment variables: `ONLY=wins_team,top_compound` to pick questions, `REPEATS=3` (default 3), `GUIDE=on,off` (default both), `NOTES=off` (default; `NOTES=off,on` also runs exploration). Output goes to `eval/logs/<UTC timestamp>/runs.jsonl` and `summary.md`. Example: `ONLY=wins_team REPEATS=1 GUIDE=on npm run eval`.
6. Local Ollama variant of the eval: `LLM_URL=http://localhost:11434/v1 LLM_MODEL=qwen3-4b-16k npm run eval` (you must create the 16K model in Ollama yourself, see Open decisions and Known issues). Add `LLM_THINK=1` to let the model think. Expect 30 to 300 seconds per question. The Worker is not needed in this mode, but the data server is.
7. Experiment runner (needs steps 1 and 2; read `experiments/2026-10-15-prompt-variants/HOW_TO_RERUN.md` first). One pilot run: `PILOT=1 node eval/run_experiment.mjs`. Full grid in batches, because each process leaks memory and died after about 40 runs: `for i in 1 2 3 4 5 6; do MAX_RUNS=14 node eval/run_experiment.mjs; done`. It skips run ids already in `eval/experiment/runs.jsonl`, so move that file aside to start fresh. Rebuild the summary only: `SUMMARY_ONLY=1 node eval/run_experiment.mjs`. A second full grid will not fit in one day's quota.
8. Regenerate ground truth (needs the Python venv): `python3 -m venv .venv && .venv/bin/pip install duckdb && .venv/bin/python eval/ground_truth.py`. This rewrites `eval/questions.json`. The experiment runner refuses to start unless the file still matches the checksum in `eval/experiment/questions.sha256`. If you change `web/src/dataGuide.ts`, also run `node eval/variants/make_v3.mjs`.

I did not start any server or run any of the eval commands while writing this. The commands come from `package.json`, the README and the runner headers.

## 4. Where the key files are

- `README.md`: short setup note. Partly out of date (see Known issues).
- `package.json`: scripts `data`, `worker`, `dev`, `build`, `typecheck`, `eval`. Deps: `@duckdb/duckdb-wasm`; dev: typescript, vite, wrangler. There is no `esbuild` entry, though the runners need it (it arrives through Vite).
- `wrangler.toml`: Worker name, AI binding, and `AI_MODEL = "@cf/openai/gpt-oss-20b"`.
- `worker/index.ts`: `POST /chat`. Passes `messages`, `tools` to Workers AI. Since 2026-10-15 it also forwards `temperature`, `max_tokens` (default 2048) and `reasoning` if the caller sends them. CORS is `*`.
- `server/serve-data.mjs`: read-only data server on port 8000 with Range support; `/manifest.json` lists the 2024 `laps` and `results` Parquet files. The default data path is hard-coded.
- `web/index.html`, `web/src/main.ts`: the page, the form, the "Explore schema" button and the notes checkbox.
- `web/src/chat.ts`: the heart of the app. The system prompt, the `run_sql` tool definition, `validateSql`, the retry loop (max 2 SQL errors, max 8 steps), `callModel`, and the module-level `history` array.
- `web/src/db.ts`: starts DuckDB-WASM, creates the `laps` and `results` views (adds `race` and `session`), `query`, `exec`, `schemaSummary`.
- `web/src/dataGuide.ts`: the hand-written data description sent with every question. It is the "V3" arm in the experiment.
- `web/src/explore.ts`, `web/src/profile.ts`: the schema-exploration feature and its deterministic SQL profile. They write notes into an in-memory `llm_notes` table.
- `eval/ground_truth.py`: computes expected answers from the raw Parquet. `eval/questions.json`: the 12 questions with expected values (generated; do not hand-edit).
- `eval/score.mjs`: the strict scorer. `eval/score.test.mjs`: its tests.
- `eval/run_eval.mjs`: the general eval runner (guide on/off, notes off/on, repeats, optional Ollama).
- `eval/run_experiment.mjs`: the frozen prompt-variant experiment runner. `eval/variants/` holds `v0.txt` to `v3.txt`, `rule.txt`, `make_v3.mjs`. `eval/experiment/` holds its logs, protocol and summary.
- `experiments/2026-10-15-prompt-variants/`: a copy of the experiment's protocol, decisions, issues, rerun steps, variants and results (verified identical to the live files, apart from `PROTOCOL.md` and `HASHES.txt` being in only one place each).
- `eval/logs/`: output of `run_eval.mjs` (two stray runs: a quota failure and a 7-run Ollama test). `eval/results-*.json`: two old-format outputs from the first runner.
- `docs/BUILD_LOG.md`, `docs/HANDOFF.md`: these documents. There was no `docs/` folder before.

## 5. Open decisions for the user

These need the owner's answer before the work goes much further.

1. Should the chat reset between questions? Today `web/src/main.ts` never calls `resetChat()`, so the whole conversation, including every tool result, is sent on each question and grows without limit. The choice is between a single-question tool (reset each time, cheapest and most repeatable), a short memory (last N turns), or a "New chat" button. Follow-ups such as "and Norris?" only work with memory.
2. Which data source: the raw Parquet (`bronze`, what the app uses now) or the cleaned dbt marts under `/Users/justin/github/off-the-pace/data/gold`? The folder `gold` exists but `ls` showed nothing in it, so I do not know whether it holds dbt marts, and I did not check the sibling repo's `transform` folder. I cannot say if it would remove traps such as the lap-grain mistake. A mart with one row per race result would make several data-guide lines unnecessary. This also decides whether `ground_truth.py` stays independent of the app.
3. Use local Ollama or stay on Workers AI? Local has no quota but took 30 to 300 seconds per question for a 4B model and leaks thinking text into answers (BUILD_LOG section 8). Cloud is fast but capped at 10,000 neurons a day on the free plan, or paid.
4. Is gpt-oss-20b the model? The switch from mistral-small-3.1-24b was never tested head to head (BUILD_LOG section 2). Decide whether to run that comparison, or try other Workers AI models.
5. Keep or remove the exploration notes feature? It showed no benefit and its save check is weak. Removing it would simplify `chat.ts`, `explore.ts`, `profile.ts`, `main.ts`, `index.html` and the eval runner.
6. Which settings should be the real defaults: max_tokens 2048 (app) or 4096 (experiment); temperature unset or 0; reasoning effort? They should match between app and eval, or the eval does not describe the app.
7. Should the repo be committed now, and what goes in `.gitignore` (logs, old results, the 2 MB `runs.jsonl`)? I did not commit anything.
8. Should the data path stay hard-coded to `/Users/justin/github/off-the-pace/data`? Moving it to an environment file or a repo-relative setting would help anyone else who clones this.

## Known issues

Each item is tagged. Details are in BUILD_LOG.md.

Repo state
- Nothing is committed. `git log` says "No commits yet on master", and every file is untracked (verified). There is no commit hash for any result; the experiment identifies files by SHA-256 instead. All earlier work could be lost with one bad command.
- `.gitignore` contains only `node_modules`, `dist`, `.wrangler`, `.dev.vars`, `.venv` (verified). It does not ignore `eval/logs/` (stray runs, including a misleading "0/1 pass" quota-failure directory), `eval/results-2026-10-14T06-54-10-175Z.json` and `eval/results-2026-10-14T07-04-29-038Z.json`, or `eval/experiment/runs.jsonl` and its 2 MB copy under `experiments/.../results/`.
- A reproducible-environment gap: `esbuild` is used by the runners but is not declared in `package.json` (verified).

Model settings are inconsistent between the app and the experiment (verified by reading)
- The model is set only by `AI_MODEL` in `wrangler.toml` (gpt-oss-20b). The runners record the model from `wrangler.toml` or a `MODEL` environment variable that is only a label, not a setting; a label can disagree with the real model.
- max_tokens: the app sends none, so the Worker uses 2048. The experiment sends 4096.
- Temperature and reasoning effort: the app sends neither. The experiment sends temperature 0 and effort "medium". There is no evidence either is honoured: two probes with different effort levels gave identical token counts, and temperature 0 was never checked by a repeat test. Treat the experiment's accuracy numbers as belonging to a configuration the app does not use.

App behaviour
- The UI never resets the chat (see Open decisions). Context grows without limit, and old tool results stay in every request.
- If the loop stops early (SQL error limit or 8 steps) while an assistant turn still has unanswered tool calls, the next question would send an inconsistent history. Inferred, not reproduced.
- `validateSql` rejects `;` and the words load, copy and others even inside string literals, accepts `LIMIT` anywhere in the text (even in a subquery) as proof of a limit, and does not block file-reading functions. The model sees at most 50 rows, though `row_count` can reach 200.
- The Worker allows any origin. Local use only.

Data guide (`web/src/dataGuide.ts`)
- Header claims it was verified against the 2024 Bahrain files. Some lines were written from memory of FastF1. Checked today against all 24 races (read-only Python DuckDB):
  - Wrong: `results.Laps` is NULL in every row, not "present in qualifying files".
  - Wrong examples: `results.Status` is only Finished, Lapped, Retired, Did not start, Disqualified. `'+1 Lap'` and `'Collision'` do not occur.
  - Partly wrong: `results.ClassifiedPosition` letters in the race are only R, W and D; E, F and N never occur; in qualifying the column is an empty string.
  - Misleading: `results.Time` is described as NULL for lapped finishers, but 137 of 138 lapped rows have a gap time.
  - Incomplete: `laps.Compound` also holds the string `'None'` (3 rows). `laps.Position` is NULL in 28 race rows.
- Unverified (no evidence anyone checked): TrackStatus code meanings, the "NULL for the first lap of a stint" claim for LapTime (225 NULL race laps is too few to be every stint start; inferred), Stint, TyreLife, FreshTyre, IsPersonalBest, IsAccurate, FastF1Generated, DeletedReason, LapStartDate, the four speed-trap columns, the Q2 top-15 and Q3 top-10 rule, and the "25 points for a win" scale. `race_id`, `index`, `TeamColor`, `DriverId` ("ignore") were never tested.
- The guide tells the model not to use outside knowledge, yet states F1 facts from outside knowledge (points scale), so the instruction contradicts the content.

Scorer (`eval/score.mjs`)
- `bahrain_clean_pace`: the "faster driver" check is a name check that passes whenever the answer names Verstappen, which any answer does since the question names both drivers. A swapped answer (medians attached to the wrong driver, or Norris called faster) can pass. I did not audit all 20 answers for swaps.
- Number and time checks pass if the expected value appears anywhere in the answer.
- A median rounded to two decimals fails the 0.5 ms test, even though the answer is close. Noted in the experiment as the reason V3 lost 2 points.
- For Ollama runs, the answer includes the model's thinking text, so a pass only means the values appear somewhere in the text.
